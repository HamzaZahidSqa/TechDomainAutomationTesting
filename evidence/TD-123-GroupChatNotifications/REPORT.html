3. What was tested

  • Four scenarios, one per creator: S1 Customer owner, S2 Customer sub-user, S3 Tech Domain owner, S4 Tech Domain team member. Each creates a work order for entity 104.
  • Rule under test (agreed with the tester): the chat room must contain the customer owner, the TD owner and the team members (263, 473, 476, 640). The customer sub-user is included ONLY when the sub-user created the work order; otherwise the sub-user must get no chat, no messages and no notifications (checked like an outsider).
  • "Work order created" notification: who received it (creator must not get their own).
  • Message delivery: owner, sub-user, TD owner and team member each send one message (REST inbox send = same effect as the web socket send). Every participant must see all messages and have a MESSAGE notification for the other senders' messages, none for their own.
  • Leak checks on 4 outsiders (TD non-team user, Neomeric customer, vendor, engineer): room not in inbox, conversation and room API forbidden, cannot send, no MESSAGE notification, no WO notification.
  • Accept (S1, S2): Tech Domain approves the customer ticket; the owner must be notified, and the sub-user only when the sub-user created the ticket (TD-125).
  • Browser evidence: sub-user, team member and non-team user log in, open the chat page and the bell.
  • Status walk on WO 962: Accepted -> Requested -> Counter -> Assigned -> Confirmed -> Check-in -> Check-out -> Work done -> Verified -> Approved. At every status: room participants, 4-way message round-trip with notifications, outsider access, and who received the status notification.

6. Findings (bugs to report)

  1. Data leak - any Tech Domain company user can join a customer conversation by opening its URL. User 641 (no team, not owner) opened /workOrder/messages/<wo>?engineerId=638 in the browser; the socket join added them as a participant. Afterwards the REST API returns the full thread to them (HTTP 200), they can post, and they receive MESSAGE notifications for every new message. Reproduced on all four work orders (961-964).
  2. Low priority / informational: the stored MESSAGE notification url is /workOrder/messages/<wo>?engineerId=null. Manually verified on WO-10956 (2026-10-09): the web app ignores it and navigates with ?chatRoomId=<room>, so clicking the notification opens the correct customer conversation. No user impact on web; only check the mobile app if it uses the url field.
  3. Security: GET /teams/:id returns every member's bcrypt password hash (members[].teamMember.password) to any company user.

Working as designed (not bugs): the customer sub-user is in the chat and gets notifications only for work orders the sub-user created (S2); for work orders created by the owner or by Tech Domain the sub-user gets no chat, no messages and no notifications (S1, S3, S4 - verified). Engineers and vendors near the site receive the marketplace broadcast "New work order available in Lahore..." when a work order is published. The creator never gets a notification for their own action. The engineer is never a participant of the customer room.
